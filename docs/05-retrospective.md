# 05 复盘

## 最难的问题

防重和重新规划需要同时成立。相同请求只插入一行，并不意味着原建议仍然可用。
如果已有占用变化后只返回缓存草稿，就会保留冲突时间；如果简单创建新草稿，又破坏防重。

实现将请求/素材身份与计划内容分开：原始硬约束保持不变，最新占用重新查询，允许更新原草稿内容。测试检查 ID、记录数、建议时间和确认状态。

## 实现收获

- 模型选择动作与业务权限是两层职责。模型可以建议时间，但不能授予自己确认权或发布权。
- 保存成功必须来自持久化工具结果；模型文字不能证明副作用发生。
- Trace 需要连接动作、参数、工具观察和后续动作，单纯阶段名称列表不足以解释动态决策。
- 离线 Mock 提升可复现性，真实模型测试才提供模型决策证据，二者应分别报告。
- 上限停止是正常运行结果，需要明确未完成，不能通过无限重试掩盖模型问题。

## 真实模型运行后的改进

第一轮中，模型把 NEEDS_INFO 当成可确认风险并尝试保存，工具拒绝了写入。这说明只检查最终状态会漏掉错误决策。调整审核状态说明后，验收同时检查模型是否在未通过审核时尝试排期。

第二轮补查场景中，模型生成了请求之外的素材编号，导致补查失败。将模型输出的素材编号限制在请求 ID 枚举后，补查工具可以执行。该限制约束参数合法性；是否补查、何时核验及何时结束仍由模型选择。原始失败 Trace 见 examples/observed-failure。

## 下一步

1. 增加更接近业务分布的素材与规则组合，按风险、冲突和确认边界分层统计真实模型结果。
2. 接入真实排期查询时，使用服务端版本号/事务锁处理并发变化。
3. 对每个新模型或提示版本保留独立评估结果，再比较决策正确率和调用成本。

以上属于扩展方向，不增加真实发布能力。
